# AGENTS.md

Instructions for AI coding agents working in this repo. Cross-tool standard ([agents.md](https://agents.md/)) — read by most coding agents (Cursor, Codex, Copilot, Claude Code, …). Tools that only read `CLAUDE.md`: create a local, gitignored `CLAUDE.md` containing `See @AGENTS.md`. ## Project

Bull Bitcoin Mobile: self-custodial Bitcoin + Liquid + Lightning wallet. Flutter/Dart, BLoC, Drift/SQLite, GoRouter, get_it DI. See [README.md](README.md) for product details.

**Repo doc map:** [README.md](README.md) = product · [ARCHITECTURE.md](ARCHITECTURE.md) = layer model & design rules · **AGENTS.md** (this file) = toolchain, conventions, commit/test rules · [FEATURES.md](FEATURES.md) = cross-feature dependency graph.

**Composition root** (where to wire a new feature): `lib/main.dart` → `lib/bootstrap.dart` (`startApp()` → startup wizard → `Bull.init()` → `runApp`) + `lib/init.dart` (service initialization) + `lib/app.dart` (root widget) → `lib/locator.dart` (get_it; `AppLocator.setup` registers core, then every `<Feature>Locator.setup`) → `lib/router.dart` (GoRouter; `AppRouter.router` spreads each `<Feature>Router`'s routes). A new feature is added in those last two files.

## Toolchain — non-negotiable

- **Always `fvm flutter` / `fvm dart`.** Never bare `flutter`/`dart`. The pinned SDK lives in [`.fvmrc`](.fvmrc); using a global SDK silently breaks builds.
- **Use the makefile.** Don't reinvent commands:
  - `make deps` — `fvm flutter pub get --enforce-lockfile`
  - `make analyze` — `fvm flutter analyze --fatal-warnings --fatal-infos` (matches CI; same check the pre-commit hook runs)
  - `make checks` — local Dart/Flutter checks: analyze + `make bull-ui-check` + `make custody-check` + `make fix-check` + `make format-check` + unit tests. Node-based custody import checks run only in CI
  - `make bootstrap` — melos workspace bootstrap (wraps `fvm dart run melos bootstrap`)
  - `make build-runner` — codegen (freezed, json_serializable, drift, flutter_gen)
  - `make translations` — `fvm flutter gen-l10n`
  - `make setup` — full first-time setup (clean + deps + build-runner + translations + hooks + ios pods on macOS)
  - `make unit-test` / `make integration-test` / `make test`
  - `make drift-migrations` — after changing Drift schema
  - `make android` / `make android release` — reproducible build
  - `make android beta` — beta tester channel APK (`.beta` applicationId, installs alongside production)
  - `make verify` — verify a built APK matches a published release
  - `make build-runner-watch` — codegen in watch mode during dev
- **Analyze the whole project, never specific files.** `fvm flutter analyze` (no path arg). CI runs `--fatal-warnings --fatal-infos` ([analyze_and_test.yml](.github/workflows/analyze_and_test.yml)) — match it locally.
- **`fvm dart fix --dry-run` must print `Nothing to fix!`** before commit. If not, run `fvm dart fix --apply` and stage the result.
- **Pre-commit hook is the floor.** It runs analyze + dart fix dry-run ([`.git_hooks/pre-commit`](.git_hooks/pre-commit)). **Never `--no-verify`.** If it fails, fix the cause.

## Database schema migration support

- Every database schema version shipped in a published release is immutable and must remain a supported upgrade source through the migration chain; `main` generally archives that published truth.
- Before the next release, `develop` keeps exactly one pending schema revision: the latest published schema plus 1. Aggregate all unreleased schema changes into that same next migration and snapshot; never bump once per feature or commit.
- Intermediate schema states that existed only in `develop` are not compatibility targets. Development installs may require a reset or reinstall; do not preserve intermediate snapshots solely for them. This never exempts a step from the idempotency rule below.
- **Only the foreground app migrates, and every migration step must still be idempotent.** WorkManager background tasks open the database on their own drift connection. drift does not serialize migrations across connections and writes `user_version` after each step, so a background task migrating alongside the app re-ran steps over a database that was already further along and left users updating from 6.12.x with a permanent startup crash (#3045). Background tasks therefore check `SqliteDatabase.isAtCurrentSchema()` and skip until the app has migrated; any new code that opens `SqliteDatabase` outside the foreground composition root must do the same. `_reportingMigration` runs each step in a transaction, so a step that fails part-way leaves nothing behind, but `user_version` is still written after the step commits and a step can be re-run in full. `onCreate` drops and recreates tables left by a first launch that never finished, and refuses if any table it does not seed holds a row. A second run of a step must leave the schema and the user's data unchanged: check before changing the schema (the `MigrationGuards` extension in `migration_guards.dart`, or catch only `duplicate column` / `already exists` and rethrow anything else), and run a data change only in the branch that makes the schema change it belongs to, or, for a seed, only while its table is empty. These guards are production correctness, never cleanup. `test/migrations_test/bull_database/migration_rerun_test.dart` re-runs every step over a current database holding user data, `migration_crash_recovery_test.dart` kills the upgrade (and a fresh install's first launch) after every commit and relaunches, and `migration_race_test.dart` races two connections from every schema fixture; all must stay green. A new step is re-run by the first automatically: seed any data it touches there, and add its schema fixture to the other two.
- Before release, verify the path from the latest published `main` schema fixture to the final pending schema. Once shipped, that migration and snapshot become immutable.

## Monorepo / melos

The repo is migrating incrementally to a [melos](https://melos.invertase.dev/) pub-workspace. The Flutter app remains at the repo root through `useRootAsPackage: true`. Current `workspace:` members (checked 2026-11-08, see ARCHITECTURE.md "Monorepo Migration" for what each one owns): `secrets`, `bull_ui`, `bull_ui_catalogue`, `primitives`, `bull_payjoin`, `bull_tor`, `screen_privacy`, `bull_logger`, `bull_pricer`, `bull_logs`. The makefile remains the canonical entry point across the workspace.

- **Run melos through the makefile** (`make bootstrap`), which wraps `fvm dart run melos` so the pinned SDK ([`.fvmrc`](.fvmrc)) is used. Never type bare `melos` (wrong SDK). For melos subcommands without a make target yet, use `fvm dart run melos <cmd>` — and add a make wrapper if it becomes routine.
- **The makefile stays canonical** for daily commands. melos does not replace it: `make deps` is still `fvm flutter pub get --enforce-lockfile`, and the reproducible build chain ([Containerfile.app](Containerfile.app), [build-android.yml](.github/workflows/build-android.yml)) does not run melos. melos is a `dev_dependency` only — never compiled into the app, so the reproducible APK is unaffected.
- **`packages/` and `features/` are reserved homes** for the migration (exception to rule #14 below): shared-foundation/infrastructure code lives in `packages/` (`lib/core`'s infra-only spirit per rule #7 applies there too); Flutter feature packages mounted by the root shell live in `features/`. Packages stay pure Dart by default; a Flutter dependency is allowed only when the package's capability inherently requires it (plugin/platform lifecycle, a sealed UI component, or implementing `bull_ui`) — never to permit feature presentation in an infrastructure package. Each extracted package gets `resolution: workspace` plus an entry in the root `workspace:` key (pattern established by melos PR #927). See ARCHITECTURE.md "Monorepo Migration" for the full rules.
- **Workspace verification is measured, not assumed.** Whole-project `fvm flutter analyze` covers the root and all members, and `make bootstrap` succeeds with `enforceLockfile: true` (verified 2026-07-30). Pub workspaces use the single root `pubspec.lock`; do not add member lockfiles. `make unit-test` runs `melos exec` over every declared member with a `test/` directory, the app included: Flutter members through `fvm flutter test`, pure-Dart members through `fvm dart test`. It calls `melos exec` directly through `fvm dart run`, because `melos run` would re-invoke a bare `melos` from `PATH`.

## Architecture — enforce, don't drift

Read [ARCHITECTURE.md](ARCHITECTURE.md) ("How the codebase actually looks today" + "The architecture we tend toward") and [FEATURES.md](FEATURES.md) before adding or moving code. **The repo is in active migration.** For the directory census (feature/domain/facade counts, non-normative, dated) see ARCHITECTURE.md "How the codebase actually looks today" — don't duplicate those numbers here, they drift. The target below is what new code must follow. Existing code may violate these rules — do not replicate violations, but don't refactor unrelated legacy in the same PR either.

Some rules below are canonical (textbook Clean/Hex Arch), others are deliberate project conventions. Both are binding here, but knowing which is which helps when an external source contradicts a rule — the project rules win inside this repo, but cite the canonical source if the conversation moves to *why*.

Hard rules:

1. **Feature isolation — facade is our chosen pattern.** Modular Flutter has several valid options (facade, abstract use-case interfaces, event bus, mediator); this codebase picks facade. **Target location**: `<feature>/public/<feature>_facade.dart`. **Current legacy** (e.g. [`labels_facade.dart`](lib/features/labels/labels_facade.dart)): facade at feature root — new facades use the target location, don't move legacy ones. Never import another feature's internals (`domain/`, `data/`, `presentation/`) — the `public/` facade is the only importable surface. **The facade *is* the interface** — a concrete class, not an `abstract interface class`; its method surface + `export` block are the contract (add an abstract interface only for DIP-to-break-a-cycle or test mocking). **It returns only the feature's published types** (the entity itself when clean and stable, else a dedicated public DTO + mapper as `labels` does) — **never** a `data/models/` model, an `application/`-internal type, or another feature's entity; the return type must be in the `export` block. Consumers wrap a facade call in **their own** use-case (rule #4).
2. **Layer direction — one chain, always.** `ui → presentation (bloc/cubit) → usecase (domain) → repository (domain interface → data impl) → datasource (data)`. **A bloc never imports a repository or a datasource** — it always goes through a use-case, the testable seam where data-layer errors are mapped to feature errors. **Use-cases are always present but stay thin: orchestration only.** Put each kind of logic in its home — **invariants in domain entities/value objects; data-shaping (mapping, aggregation, caching) in the repository; orchestration in the use-case**. Pushing data-shaping or invariants into a use-case is the "fat use-case" smell — move it down. The inward-only dependency rule is [hexagonal-canonical](https://alistair.cockburn.us/hexagonal-architecture); the MVVM-spine + repository is the official [Flutter guide](https://docs.flutter.dev/app-architecture/recommendations).
3. **Watchers go through use cases**, not repositories. `watcher → use case → repository`.
4. **BLoCs are thin — in our architecture.** No orchestration, no business decisions, no complex transforms; those live in use cases. ([bloclibrary.dev](https://bloclibrary.dev/architecture/) treats the bloc layer itself as the business-logic layer above repositories — our stance is a deliberate Clean-Arch refinement, not bloclibrary canon.) **Project convention**: never call another feature's facade directly from a BLoC — wrap it in your own feature's use case, and the BLoC calls that wrapper. This is the cure for "business logic in presentation", ARCHITECTURE.md's most common pitfall.
5. **Local widget state stays in `StatefulWidget`.** BLoC/Cubit is for business state only — what other layers care about. Form-field focus, animation controllers, expanded/collapsed panels, scroll positions: keep them in widget state. Mixing the two makes BLoC tests flaky and bloats state classes.
6. **Repository: abstract interface in `domain/`, impl in `data/` — don't over-abstract the rest.** Declare the contract as `abstract interface class <Noun>Repository` in `domain/repositories/<noun>_repository.dart`; put the implementation in `data/<noun>_repository_impl.dart` next to its datasources — no second `repositories/` folder. A datasource wraps one external system and is a **private member** of its repository. One repository is enough for trivial CRUD; add a separate datasource only for real transformation or multiple backends. **Boundary rule (never bends):** a repository's public signatures use only domain types (entities, value objects, `Result<Entity, …>`); wire models, library types, JSON `Map`s and DTOs never cross the boundary. *(Legacy leak, don't replicate: `WalletAddressRepository` takes a `WalletModel` param.)* **Entity and model are always two separate types** (entity in `domain/entities/`, model in `data/models/`, mapper between) — never collapse them. The entity is **self-validating** and carries no serialization; the model is **pure data**. Cap is two types per record — see [Flutter recommendations](https://docs.flutter.dev/app-architecture/recommendations) on the five-types-per-record pattern being verbosity for large apps only. Value objects are for correctness-critical primitives (amount/sats, address, fee rate), not every field.
7. **`/lib/core` is legacy and disappears; the shell is composition only.** Add nothing to `lib/core`, neither logic nor wiring. A change that touches a `lib/core` domain extracts that part into its owning package or feature, so its `lib/core` diff is net negative; never relocate it to root `lib/` just to shrink that diff. What remains there until extraction is infrastructure only, with no feature/business logic. **Dated exception (2026-11):** the wallet readers stay in `lib/core/wallet` until the capability split; during the single-writer cutover only deletions and delegation to the single-writer sync package (`packages/transaction_sync`, introduced by the wallet sync PRs) are allowed there, no new logic or wiring. The shell (`lib/*.dart`) holds entry points, ordered bootstrap and lifecycle calls, app-level navigation, capability selection and calls to each module's published setup API. It implements nothing: no storage queries, mapping, grouping, wallet/signing/sync policy, recoverable error translation, presentation or strings; each package or feature constructs its own internals. A port does not imply a shell adapter: implement it in the module that may depend on both sides. A root adapter is exceptional: it documents the concrete cycle it breaks and its removal condition, and only forwards public capabilities. Root files that predate this rule and construct a module's internals (`lib/payjoin_setup.dart`, `lib/recoverable_payjoin.dart`, `lib/payjoin_runtime_adapters.dart`, `lib/report_logger_adapter.dart`) are tracked debt, moved in their own PRs. See ARCHITECTURE.md "Monorepo Migration".
8. **Shared value objects belong in `packages/primitives`**, the canonical package. During migration, compatibility types and exports may remain in `lib/core/primitives/`; see [FEATURES.md](FEATURES.md). Before adding one, search both locations and `lib/` for a same-intent type; reuse it rather than creating a duplicate.
9. **Prefer rich domain models** — methods that enforce invariants, not anemic DTOs mirroring DB rows. ([Fowler's anemic-domain anti-pattern](https://www.martinfowler.com/bliki/AnemicDomainModel.html) is widely cited but not universal; this is our preference, aligned with ARCHITECTURE.md's "Anemic Domain Models" pitfall.)
10. **No raw colors.** Always pull from the theme. If the user describes a color in plain language, pick the closest theme color that works in both light and dark mode. Don't edit theme files unprompted.
11. **Failures — one sealed family per feature, `*Failure` not `*Error`.** Three words, kept apart: **`Exception`** = thrown infra (data layer, caught at the boundary); **`Error`** = a `dart:core` programmer bug, never caught; **`Failure`** = a modeled, recoverable **value** in `domain/`. Define a sealed `<Feature>Failure extends Failure` in `domain/<feature>_failure.dart`, **Flutter-free**; cross-cutting modes (network, storage-locked, not-found, timeout, auth, device, insufficient-funds) come from the shared `sealed CoreFailure` in `lib/core/failures/` (alongside the `Failure` base; `lib/core/errors/` is the legacy graveyard). Map foreign errors at the boundary; never leak another layer's or feature's type. **Translation is a presentation extension, not a method on the failure:** `presentation/<feature>_failure_l10n.dart` exposes `toTranslated(BuildContext)` — the only place `context.loc`/`flutter` touches a failure (keeps `domain/`+`data/` Flutter-free); the `sealed` switch makes a missing user message a compile error. **The end user never sees a dev string:** the catch-all variant returns a **generic** localized message (`oopsSomethingWentWrong`), never the raw `logMessage` — `unexpected: (m) => m` leaks dev detail. **Propagation:** repositories return `Result<T, F extends Failure>` (`Ok`/`Err`, `@useResult`; helpers `fold`/`map`/`mapErr`); `throw` only for `dart:core` bugs ([Flutter Result](https://docs.flutter.dev/app-architecture/design-patterns/result)). The **repository** is the one `try/catch` boundary (or the feature **use-case** when wrapping a shared core repo that still throws); use-cases forward/compose `Result`s; the bloc `switch`es and holds the typed `<Feature>Failure` in state; the UI renders `failure.toTranslated(context)`. **Migration (#1895) is sanctioned and staged** — bring a feature fully in line when you touch it, one feature per PR. **Legacy (don't replicate):** `BullException`; hardcoded English; `<Feature>Error` naming; `toTranslated` on the error; per-layer error-file splits; `fund_exchange`'s singular prefix.
12. **Acyclic feature graph.** Check [FEATURES.md](FEATURES.md) before adding a dependency.
13. **Keep the dependency graph live.** Any PR that adds a feature, removes a feature, or changes which other features it consumes via `public/` facades **must** update the mermaid graph in [FEATURES.md](FEATURES.md) in the same commit. The graph is documentation only if it matches the code — if you change one without the other, both become useless.
14. **Folders justify their existence — files don't justify folders.** A tiny piece of code is one file with a role suffix, not a folder of one file:
    - One use case → `<feature>/domain/<verb>_<noun>_usecase.dart`. Don't create `domain/usecases/` for a single file.
    - One entity → `<feature>/domain/<noun>.dart`. Don't create `domain/entities/` for a single file.
    - One datasource → `<feature>/data/<noun>_datasource.dart`. Don't create `data/datasources/` for a single file.

    Create the folder the moment a **second** file of that kind appears (or you know it's imminent in the same PR). Don't pre-create empty folders or use `.gitkeep`. Suffix carries the role; path carries the layer.

    **Exception (melos migration):** `packages/` and `features/` are intentionally pre-created with `.gitkeep` as reserved workspace homes for the in-progress monorepo migration — do not remove them or treat them as a rule-#14 violation. See the Monorepo / melos section.

15. **Enforce with the compiler, not hope.** Repository contracts → `abstract interface class` (forbids `extends`, forces `implements`); lock finer capabilities with `@Deprecated.implement()` / `.instantiate()` / `.extend()`. Failure families and multi-case states → `sealed`; a missing `switch` case is a compile error. `Result`-returning repo methods → annotate `@useResult`. Cross-feature and `data/`-from-`presentation/` bans → a rule in the first-party analyzer plugin system (Dart 3.10+); under melos, package boundaries + the `implementation_imports` lint make them hard errors. All available in the current toolchain (Flutter 3.41/3.44 bundle Dart 3.11/3.12) — no point-release dependency.

When a request would break these rules, explain why and propose a compliant alternative. Don't silently comply.

When you **work in** a feature, file, or folder that already violates these rules (legacy, a drifted hexagonal module, a leaked boundary), don't silently work around it and don't quietly copy it. **Flag it and offer a fix:** name the specific rule it breaks and propose a **scoped refactoring** to bring it into line — as its **own** atomic commit/PR, separate from the task at hand. Then let the developer decide: take it now, defer it, or skip it. Never fold an opportunistic refactor into an unrelated change (that breaks atomic commits). This is the "leave it cleaner than you found it" rule from [ARCHITECTURE.md](ARCHITECTURE.md)'s intro, kept compatible with atomic commits — surface the opportunity, don't force it.

## Null safety

Never introduce the postfix non-null assertion operator (`value!`). A missing value must be handled explicitly: promote a checked local variable, use pattern matching, return a typed failure, or render the loading, unavailable, or error state. Do not replace an assertion with an unchecked cast or a fabricated default that hides missing data. When touching an existing assertion, check the lifecycle and asynchronous paths that can invalidate its assumption; cover a recoverable missing value with a regression test. This rule concerns non-null assertions, not boolean negation (`!condition`) or inequality (`!=`).

## Naming conventions

Codified from a sweep of the actual codebase. ARCHITECTURE.md is silent on most of these; the rules below reflect what the dominant code already does. Where two conventions exist, the recommendation is the more common one — migrate toward it, don't replicate the minority.

**Folders** (inside a feature):

| Folder | Convention | Notes |
|---|---|---|
| `domain/entities/` | plural | rich models + value objects |
| `domain/repositories/` | plural | the single `repositories/` folder — **abstract** interfaces (contracts) |
| `domain/usecases/` | plural, no underscore | the canonical use-case home (~80% already here) |
| `data/datasources/` | plural, no underscore | not `data_sources/`; one external system each |
| `data/models/` | plural | wire/persistence model — **1 per entity, always separate from the entity** |

| `data/` (repo impl) | — | `<noun>_repository_impl.dart` lives directly here |
| `presentation/` | — | bloc/cubit + state + event |
| `ui/screens/`, `ui/widgets/` | plural | |
| `public/` | — | facade lives directly inside |
| `watchers/` | plural, optional | drives use-cases, never repositories |

> Deprecated — converge away (see ARCHITECTURE.md "Convergence"): `application/`, `adapters/`, `interface_adapters/`, `frameworks/`.

**Files** — `snake_case`, singular suffix:

| Entity / value object | `<noun>.dart` | `wallet.dart`, `auto_swap.dart` |

| Cubit | `<feature>_cubit.dart` | `settings_cubit.dart` |
| State | `<feature>_state.dart` | `send_state.dart` |

| Locator | `<feature>_locator.dart` | `wallet_locator.dart` |
| Failure (family) | `<feature>_failure.dart` (domain) + `<feature>_failure_l10n.dart` (presentation) | per rule #11 |

**Classes** — `PascalCase`, matching local quirks:

- **Use cases**: `<Verb><Noun>Usecase` — **lowercase 'case'**, never `UseCase`. Codebase-wide convention (`GetSettingsUsecase`, `UpdateTorSettingsUsecase`, `BroadcastBitcoinTransactionUsecase`). Single public entry method **`execute(...)`** (206 of 209 use-cases as of 2026-06, non-normative; never `call`).
- **Datasources**: `<Name>Datasource` — **lowercase 's'**, never `DataSource`. Codebase-wide (`BdkWalletDatasource`, `BoltzDatasource`).
- **Repositories**: abstract interface = `<Name>Repository` (`abstract interface class`, in `domain/repositories/`); concrete impl = `<Name>RepositoryImpl` or `<Tech><Name>Repository` (in `data/`). Pick the technology prefix when the backing tech is meaningful; use `Impl` when the technology label would be awkward.
- **Entities & value objects**: bare noun, **no `Entity` suffix** (`Wallet`, `WalletUtxo`, `TransactionOutput`). Legacy outlier `LedgerDeviceEntity` — don't replicate.
- **Models (wire/persistence)**: `<Noun>Model` (`WalletUtxoModel`) — in `data/models/`, freezed; serialization only, never crosses the repository boundary (rule #6).
- **Mappers**: `<Noun>Mapper` (`WalletUtxoMapper`) — in `data/mappers/`; translates model ↔ entity.
- **Non-repository domain interfaces**: `<Name>Port` (`BlockchainPort`, `ElectrumConnectivityPort`) — a capability abstraction that is not a repository; lives in `domain/`. Repository interfaces use `<Name>Repository`, never `Port`. (The `Port` *suffix* stays for these; only the hexagonal *folders* `application/`/`adapters/`/`frameworks/` are deprecated.)
- **Bloc/Cubit**: `<Feature>Bloc` / `<Feature>Cubit` (`SendBloc`, `SettingsCubit`).
- **State / Event**: `<Feature>State` / `<Feature>Event`, sealed with freezed when there are multiple cases.
- **Facade**: `<Feature>Facade` (`LabelsFacade`).
- **Watcher** (when introduced): `<Subject>Watcher`.
- **Failure**: one sealed `<Feature>Failure` family per feature in `domain/<feature>_failure.dart` (base `Failure`); never `<Feature>Error` — `Error` is reserved for `dart:core` bugs. Translation extension `<Feature>FailureL10n` in `presentation/`. See rule #11.

When the same role exists with two names in the codebase, use the dominant one and flag the outlier as legacy. Don't rename outliers in unrelated PRs — that breaks atomic commits.

### Member ordering

Inside a class, declare members in this order, with a blank line between each group:

1. **Instance fields** — the object's state. Reading these first tells you *what the thing is*.
2. **Constructor(s)** — how it's built, on top of the fields you just read.
3. **Methods** — its behaviour, including `@override`s.

```dart
class Amount {
  final BigInt sats;

  Amount(this.sats) {
    if (sats < BigInt.zero) throw ArgumentError('Amount cannot be negative');
  }

  bool get isDust => sats < BigInt.from(546);
}
```

This is fields-first on purpose: our domain, value, and error types are defined by their state, so surfacing it first reads most naturally. It is a soft convention — the analyzer does not enforce member order, so keep it consistent by hand and in review.

**Do not enable the `sort_constructors_first` lint.** It enforces the *opposite* order (constructor before fields); turning it on would fight this convention and churn every class. Widgets, whose constructor is effectively their public API, may keep the constructor first if that reads better there — don't reformat existing widgets to satisfy this rule.

## UI Kit — reuse first, build the kit as you go

The codebase is migrating toward a real UI Kit. The skeleton already lives in [`lib/core/widgets/`](lib/core/widgets/) (`buttons/`, `cards/`, `inputs/`, `lists/`, `dropdown/`, `bottom_sheet/`, `text/`, `selectors/`, …) and theme tokens in [`lib/core/themes/`](lib/core/themes/). Today the same widgets get re-implemented per feature (`_SaveButton`, `_ConfirmButton`, `_BottomButtons` …) — stop adding to that pile.

The go-forward home for the kit is the **`bull_ui` design-system package** (`packages/bull_ui`; see ARCHITECTURE.md "Design-system package"). Provenance: **`BB*` = legacy `lib/core/widgets`, `Bull*` = `bull_ui`**. A feature whose UI is built on the kit imports only `package:bull_ui/bull_ui.dart` for widgets — never `package:flutter/material.dart`/`cupertino.dart`/`widgets.dart`. Migration is incremental, so both still exist; prefer a `Bull*` widget when one exists, otherwise follow the workflow below against `lib/core/widgets/`.

Workflow when you need a widget:

1. **Search `lib/core/widgets/` first.** If something close exists, use it.
2. **If close but missing a variant**, extend the core widget (new prop, new constructor) rather than fork. One source of truth, no copy-paste.
3. **If genuinely new and reused by ≥ 2 features**, put it in `lib/core/widgets/<category>/` from the start — that *is* growing the UI Kit.
4. **If used by exactly one feature**, it lives in `<feature>/ui/widgets/` — but write it composable enough to be promoted later (no hardcoded colors, no hardcoded text, take callbacks not bloc refs).
5. **Widgets never live under `adapters/`, `frameworks/`, `domain/`, or `application/`.** UI goes in `ui/` or `lib/core/widgets/`. Full stop.
6. **No hardcoded user-facing strings.** Always `context.loc.<key>` — the `BuildContext` extension (`build_context_x.dart`) that wraps `AppLocalizations.of(context)`; it is the dominant convention (≈2564 uses vs 3 raw `AppLocalizations.of`, as of 2026-06, non-normative). Manage keys in [`localization/`](localization/) with [`tools/arb.dart`](tools/README.md) (`fvm dart run tools/arb.dart help`) — don't hand-edit the `.arb` files — then run `make translations`. A duplicated literal across screens means a missing l10n key.
7. **Theme tokens only** — colors, spacing, typography pulled from the theme. See rule #10 above.

When you spot a duplicate of an existing core widget in feature code, flag it in the PR description as a follow-up cleanup. Don't silently leave it. Don't fix unrelated duplicates in the same PR either — that breaks atomic commits.

## Commits — atomic + Conventional

Format: `type(scope): description`

- **type**: `feat | fix | refactor | chore | docs | test | ci | build | perf | style`
- **scope**: feature folder name (`wallet`, `send`, `payjoin`, `swap`, `core`, `ci`, `hooks`, …) — lowercase, single noun.
- **description**: imperative, lowercase, no trailing period, ≤72 chars total subject line. Human-friendly and compact — describe the *why* if non-obvious; the *what* is in the diff.

Rules:

- **Atomic.** One logical change per commit. A feature + its refactor = two commits. A fix + cleanup = two commits. Independently revertable.
- **No `Co-Authored-By` trailer.**
- **No `--no-verify`.** Pre-commit must pass on its own.
- Reference the recent history (`dc3642801`, `14cce2ad6`, `1fecb0bb8`) for style.

## Verify before suggesting

**Your training data is stale; the ecosystem isn't.** Flutter, Dart, BDK, Boltz, payjoin, freezed, drift, go_router, bloc — all churn fast. Pasting an API or library version from memory wastes the user's time.

Before recommending a library, API surface, syntax, flag, version, or pattern:

1. **Anchor on the current date.** Run `date -u +%Y-%m-%d` — your knowledge cutoff isn't today.
2. **Cross-check at least one trustworthy source**, freshness-matched to that date: official docs (pub.dev, docs.flutter.dev, dart.dev), the project's own GitHub (`gh release list`, `gh issue list`), StackOverflow answers from the last ~2 years, or Reddit (`r/FlutterDev`, `r/dartlang`).
3. **Cite the source** in chat or in the PR description: title + URL + a date stamp. "Per pub.dev/packages/foo (2026-04-15) …".
4. **If you can't verify, say so explicitly** — "I think X but couldn't confirm" beats stating a wrong API confidently.

This applies equally to architectural suggestions, tooling, CI tricks, command flags, and security recommendations. Confidence ≠ correctness.

## Logging and error reporting

Use `package:bull_logger/bull_logger.dart` and its `log` API. **Our levels deliberately differ from the usual logging convention: `INFO` is debug-console chatter, not a persisted diagnostic.** All levels print to the console only in `kDebugMode`; the on-disk TSV files are the logs users can share with support.

| API | On-disk support log | Reporter route |
|---|---|---|
| `log.info` | No | None |
| `log.fine`, `log.finer`, `log.finest` | Yes | None |
| `log.config` | Yes | None |
| `log.warning` | Yes | None |
| `log.severe` | Yes, flushed | Error capture |
| `log.shout` | Yes, flushed | Exception capture, or an info-level message when no exception/trace pair is supplied |

- **Choose a destination deliberately.** Use `info` for repetitive development traces (individual polls, relay attempts, fee previews). Use `fine` for milestones an exported log must reconstruct, `config` for configuration, and `warning` for recoverable failures. Record a persistent failure and its recovery as bounded state transitions rather than persisting every failed poll. Keep messages short and structured: mnemonic-like word sequences can be redacted by the local sanitizer.
- **Sentry is a separate, conditional route.** On the normal path, `severe` and `shout` invoke the optional reporter; other logger methods do not. In the app, capture requires the release SDK to be enabled and user consent. Background tasks do not call `Report.init`, so they currently keep their diagnostics on disk. Reentrant calls inside the log listener and internal logger failures do not invoke the reporter; their local diagnostics are best effort. Automatic SDK events have their own consent-gated paths; do not bypass the app's reporting boundary with feature-level SDK calls.
- **Local redaction is not Sentry redaction.** `Logger._sanitize` applies to disk and console output, not to the objects passed to the reporter. `Report.beforeSend` removes exception values, breadcrumb messages/data and requests, and attempts to clear frame variables; it does **not** remove every string. In particular, `bull.dev_message` and `shout` message events can retain the supplied message. Use fixed labels or explicitly allowlisted structured metadata. Never interpolate payment URIs, addresses, txids, amounts, credentials or user input into reporting messages. An `error:` argument can also expose its text in local logs: reduce sensitive foreign causes to safe type/status metadata before logging, and never rely on a scrubber to make secrets safe.
- **Payjoin uses the same vocabulary.** `AppPayjoinLogAdapter` maps `info`, `fine`, `warning` and `severe` directly to the homonymous wallet methods, without code-based remapping or a package-only debug level. Routine traces use `info`; persisted milestones use `fine`. Both require an explicit code. Remove context-free routine calls rather than emitting indistinguishable lifecycle noise. `PayjoinLogger` accepts structured fields only, without free-text message arguments; the host renders `PayjoinLogCode.description`. Structured session references retain 16 hex characters; the adapter displays their first 7 characters after the role, without a `ref=` label. Preserve fixed codes, roles and safe session references; never forward a raw foreign exception message.
- **Verify routing when changing logging.** Extend the contract tests in `packages/bull_logger/test/logger_reporter_test.dart` and the affected adapter tests. Check both what reaches the shared log and what invokes the reporter; a console line alone does not prove that support or Sentry will receive it.

Sources of truth: [`logger.dart`](packages/bull_logger/lib/src/logger.dart), initialization in [`logging_setup.dart`](packages/bull_logger/lib/src/logging_setup.dart), [`report.dart`](lib/core/utils/report.dart), the app's [`ReportLoggerAdapter`](lib/report_logger_adapter.dart), foreground wiring in [`init.dart`](lib/init.dart), background bootstrap in [`handler.dart`](lib/core/background_tasks/handler.dart), and [`AppPayjoinLogAdapter`](lib/payjoin_runtime_adapters.dart).

## Security (self-custodial wallet — treat as load-bearing)

This app holds users' keys. A leak is not a bug, it's a loss of funds. Hold these as hard as the architecture rules:

- **Only `packages/secrets` touches the keystore that holds the seeds.** No new import of `flutter_secure_storage` outside it (the app's own secure store in `lib/core/storage` is the one allowlisted exception), no import of `package:secrets/src/`, and never an `// ignore:` of `invalid_use_of_internal_member`. `make custody-ci-check` fails on any of them in CI; local `make custody-check` runs the Dart key-material gate. Rules: `tools/pr_governance/custody.js`.
- **Never log secrets.** Mnemonics, seeds, xprivs, PINs, raw key material never reach logs, Sentry, or analytics. Scrub before reporting; assume anything logged is exfiltrated.
- **Secrets are ephemeral.** Read from `flutter_secure_storage` at point of use; don't cache key material in long-lived bloc/singleton state. Treat a revealed value as short-lived.
- **Sealed UI for display.** Show a secret through a widget that reads it internally and never returns it (the `MnemonicView` pattern — see ARCHITECTURE.md "Sealed UI as a security tool"); never add a getter that hands the raw value to a caller.
- **Block capture on secret screens** — `no_screenshot` plus exclusion from the semantics/accessibility tree.
- **Validate at the domain boundary.** Addresses, amounts, descriptors are value objects that reject invalid input at construction (rule #9) — never trust a raw string deeper in.
- When a change touches key material, signing, or backup/recovery, **say so explicitly in the PR** so it gets the right review.

- A robot on a coordinator (`CoordinatorClient.fetchRobot` and `fetchKnownRobot`, `FetchRobotUsecase`, `docs/spikes/robot-coordinator.md`): the answer of a coordinator is accepted only when its hash id and nickname are the ones this device derives from the token, compared before any key of the answer is read, and its OpenPGP key pair is either the pair this very first contact sent or a pair the robot's token proves (`UnprovenCoordinatorRobot.prove`: the private key unlocks with the token and holds the secret values of the public key; a coordinator receives the SHA-256 of the token, never the token, and the S2K that locks the private key is salted and iterated over the token itself, so only a holder of the token can have made that pair). Anything else is a typed failure (`RobotHashIdMismatch`, `RobotNicknameMismatch`, `RobotPgpKeyNotProven`), never a silent change of key as in the official client, which adopts whatever pair a coordinator returns. So the pair is not stored: a read with the short header sends no pair and always proves the pair it gets back, after a restart or for a robot of an imported key alike. The proof holds only because each secret part is locked by an iterated and salted S2K over the token (`ProtectedSecret.provesPassphraseWith`, which the parser requires and the proof checks again): a simple S2K over SHA-256 would derive exactly the token hash every coordinator holds. « Proven » means made by a holder of the token, nothing more: a coordinator can return any genuine pair of the robot it ever received (the use case makes a new one for each first contact the user asks for, and sends that same pair again when it retries that request after a busy answer), a different one at each read, so a proven pair is not necessarily the one the coordinator stored first nor the one it will check signatures with; and `CoordinatorRobot.pgpKeyProven` is the coordinator's word, like `found` (it makes it true by returning the very pair sent in other packet framing), so no screen may rely on it alone to say that a robot existed before. A proven pair is re-encoded from the packets the proof checked (primary key, certified user ID and its certification, the selected subkey and its binding, each signature without its unhashed area): whatever else a coordinator put in the blocks is dropped, so what a robot holds is bounded by the key its owner made. A proof hashes 32 MiB of SHA-256 for a key of the official client or of Troc, and at most `PgpLimits.proofHashedBytes` (62 MiB, both secret parts and every S2K pass together), a pair that would hash more, one GnuPG protected at its largest count included, being refused before anything is hashed; it wipes the passphrase bytes and the secret values it unlocked, and the robot keeps only the locked pair. `FetchRobotUsecase` makes the pair of each first contact itself, for that robot, after the binding and before the request, so that no caller can send a pair this device did not just make for that robot (a pair that comes back as sent is taken without a proof): a first contact is a `RobotFirstContact` (`RobotContact.firstContact`), which keeps the pair made at its first request and sends it again at each request made with it, so that a request sent again never hands the coordinator a second pair, and a read back is a `RobotReadBack`; it makes and proves pairs only through `RobotKeyComputePort`, whose implementation `IsolateRobotKeyCompute` runs each in `Isolate.run`, from static methods so that the isolate gets nothing but its one argument. What crosses to the isolate: to make a pair, the robot's whole `RobotIdentity` (its token, both forms of its token hash and its two Nostr secret keys); to prove one, the `UnprovenCoordinatorRobot`, which holds the token, the two blocks of the answer and public facts only. That isolate shares the heap of the app's isolates, so it keeps the screens fluid, it does not keep the token or the unlocked values apart in memory, and copies stay unwiped until collected: the token itself (a `String`, which cannot be wiped), its bytes in the list `s2kIteratedSalted` builds the salt and the token from and in the hash's own buffers, the big-endian copy of the scalar and the list made to reverse it, the key objects `pinenacl` builds, and the copies of the identity a message makes. The answer itself is parsed on the calling isolate before the proof, three times: a key block with more than `PgpLimits.keySignatures` (8) signature packets, where a robot key has 2, is refused before any is verified, so an answer costs at most 24 Ed25519 verifications there (a hostile block of 32 packets cost about 80, about 300 ms under JIT, before that bound, #69). `features/p2p/test/robot_bindings_architecture_test.dart` pins that only that file proves a robot or makes a pair, that nothing in the feature unlocks one or refers to the package's internals of the proof (`RobotPgpKey.proveMadeBy`, `CoordinatorRobotAnswer.parse`, `UnprovenCoordinatorRobot.parse`), and that no file of `lib/` silences a diagnostic but those the generators write (lints and unused imports) and the one `experimental_member_use` of the table migration of `p2p_database.dart` (« One robot, one coordinator » below); it resolves every Dart file of `lib/`, the translations included. - **The trade's state machine (#86, phase 2): the only place that turns a coordinator's answer into what a screen may show or a wallet may pay.** `features/p2p/lib/src/domain/trade/`: `TradeStatus.from(previous:, answer:, terms:, now:, reader:)` is pure (no clock, no I/O, no randomness) and gives one class per status a taker can see, from a `TradeAnswer` (the `CoordinatorOrder` of a read, a take or a cancel, or error 1043 or 1044: `TradeAnswer.ofRead`) checked against the `TradeTerms` fixed at the take (`TradeTerms.take` from the public order, or `TradeTerms.takeRead` from a read of it, the amount taken and the coordinator's `taker_fee`, refused with `TakerFeeTooHigh` above `TradeTolerances.takerFeeCeiling`, 1 %) and against the trade's history (`TradeTrail`: the last position, the payment hash of the first invoice of each step, the last deadline, the pre-take's last read and deadline, any breach of trust, and whether the history is unknown). There is no status without a trail, and a trail belongs to one trade (order, coordinator, network, role: `from` refuses other terms with `TradeOrderMismatch`). A trade starts from the take's own answer, `TradeStatus.afterTake(OrderTakeStarted, …)` (the package's outcome that only `takeOrder` gives); otherwise `previous` is the last status, or `TradeStatus.beforeFirstRead(trail)` of a trail that only `TradeTrail.restore(record, terms:, now:)` (a recorded trade), `TradeTrail.forPendingTake` (a take whose answer was lost and which has no trail recorded yet: only a take's answers may come first) and `TradeTrail.recovered` (a trade found by recovery: anything may come first, and every status carries `TradeHistoryUnknown`, so the wallet never pays on it) make; the take's own fresh trail is private to the state machine, and `trade_records_test.dart` pins that only `lib/src/domain/trade/` and `lib/src/domain/usecases/trade/` name these factories. A restored trail at an end gives an end at once. The edges are `TradeEdges.steps`, each single move of the reference backend for a taker with its roles and its lines (pinned by `trade_status_test.dart` against a list written out apart from the table); any path of them is allowed between two reads, an unlisted edge to a status that goes on gives it with `TradeStatusUnexpected`, an unlisted edge to an end, a status a taker is never shown, a role, coordinator or order that is not the trade's, and any return to the bond step but from the pre-take are refused as answers (the last status stays, with the warning); a breach of trust (those, and an invoice whose payment hash is not the first of its step) is remembered by the trail, and every later status carries `CoordinatorInconsistent`. A terminal status is never left. Error 1044 during the pre-take is `PreTakeUnavailable`, not an end, until the pre-take's deadline and `TradeTolerances.coordinatorLoops` have passed: a maker who pauses the order gives the pre-taker 1044 and the pre-take comes back after the pause (`api/views.py:269-275`, `api/logics.py:1758-1783`). Show each message's signature time (`DecryptedChatMessage.signedAt`) and flag a message signed earlier than an earlier-indexed message of the same sender. A message this robot sent again after a post whose outcome was unknown is a legitimate duplicate: labelled as sent twice, not as a breach.
  - Decrypt a `self` message with the robot's own key and a `peer` message with the pinned key; mark a message whose signature does not verify (« Signature not valid: this message may not come from {nick}. », § 3.6); a message of an `unknown` sender is from neither party and is never checked as the peer's; show `notPgpMessage` and `tooLong` as unreadable, without text.
  - After a post whose outcome is unknown, read again from the offset posted with and look for the message with `ChatPage.indexOf`: found, the coordinator shows it as stored; not found, show it as « not confirmed: it may still reach your peer », never « not sent » nor « failed » (a coordinator can keep it out of this robot's pages and still deliver it, give it the peer's nickname, or change one character of it); if the user sends it again, send the same `OutgoingChatMessage`, never a new encryption of the same text.
  - After a refusal with `ChatRefused.fromLastRead`, read the order again before telling the user anything: the last read may be stale.
  - `ChatPageTooLarge` (a peer can post enough to cause it, from offset 0, which is where a restart reads from): tell the user the history is too large to read from the start; never skip silently to a later offset such as the order's `chat_last_index`, which leaves out the earlier messages, the payment details among them; offer to read only the newer messages as the user's explicit choice, and say then that earlier ones are not shown. The package cannot read the history in parts: the coordinator answers every message above an offset at once, and the indexes are known only by reading them.
  - Check the text's length with `OutgoingChatMessage.textBytesOf` against `maxTextBytes` as the user types; never log, print, store or put in a report the plaintext, the armored or wire text of a message, or the peer's key (§ 4.3); keep the chat in memory only; poll through `RobotRequestLimiter`, every 5 s while the chat is shown (§ 3.6, § 3.8); refuse to send the robot's token (the package does) and the payout text of the trade (§ 4.2).
